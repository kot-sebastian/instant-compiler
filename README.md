# Instant Compiler

**English** | [Polski](README.pl.md)

A compiler for the **Instant** language targeting the **JVM** (Jasmin assembler → `.class`) and
**LLVM** (`.ll` → `.bc`), written in Haskell. Built as a university assignment for the
Compiler Construction course (MRJP) at the University of Warsaw (task statement, in Polish:
[`[PL]task-description.pdf`](%5BPL%5Dtask-description.pdf)).

```text
x = 2 + 3 * 4;      ← assignment: prints nothing
x - 1;              ← expression: prints 13
(x - 4) / 2         ← prints 5
```

## Quick start

```bash
make                                   # builds ./insc_jvm and ./insc_llvm
./insc_jvm test/programs/basic.ins     # → test/programs/basic.j + basic.class
java -cp test/programs basic
./insc_llvm test/programs/basic.ins    # → test/programs/basic.ll + basic.bc
lli test/programs/basic.bc
```

No GHC? See [Running in a container](#running-in-a-container-no-ghc-needed).

## Requirements

| Tool | Used for | Tested with |
|------|----------|-------------|
| GHC + `cabal` (≥ 3.4) | building the compiler | GHC 9.10, 9.12; cabal 3.12, 3.14 |
| Java (JRE/JDK) | running Jasmin (`lib/jasmin.jar`) and the generated `.class` files | OpenJDK 17, 25 |
| LLVM: `llvm-link`, `lli` | linking with `lib/runtime.bc` and running `.bc` files | LLVM 14, 22 |
| `make`, `bash` | the Makefile and end-to-end tests | – |

`alex` and `happy` (lexer/parser generators) **do not need to be installed**: cabal builds them
itself (`build-tool-depends`). `bnfc` is only needed when changing the grammar (`make grammar`).

Installing the tools:

```bash
# Fedora
sudo dnf install ghc cabal-install llvm java-25-openjdk-headless make
```

```bash
# Debian / Ubuntu
sudo apt install ghc cabal-install llvm default-jdk-headless make
```

```bash
# Any Linux / macOS – the official GHCup installer (https://www.haskell.org/ghcup/)
curl --proto '=https' --tlsv1.2 -sSf https://get-ghcup.haskell.org | sh
```

After installing cabal, run `cabal update` once.

## Building

```bash
make          # = make build: cabal build + copy insc_jvm and insc_llvm to the project root
make clean    # removes dist-newstyle/ and insc_jvm, insc_llvm
```

The first build downloads dependencies from Hackage (including alex/happy) and takes a few
minutes; subsequent builds take seconds.

Haskell libraries (besides `base`): `array` (code generated by alex/happy), `containers`
(variable maps), `mtl` (`State`/`ExceptT` monads), `filepath`, `directory`, `process` (driver:
paths, files, invoking Jasmin/llvm-link). The tests additionally use `QuickCheck`.

## Usage

```text
insc_jvm  [--emit-only] FILE.ins...
insc_llvm [--emit-only] FILE.ins...
```

| Command | Output (next to the input file) |
|---------|---------------------------------|
| `./insc_jvm foo/bar/baz.ins` | `foo/bar/baz.j` (Jasmin) and `foo/bar/baz.class` |
| `./insc_llvm foo/bar/baz.ins` | `foo/bar/baz.ll` (textual LLVM IR) and `foo/bar/baz.bc` (bitcode linked with the runtime) |
| `--emit-only` | only `.j` / `.ll`, without running Java/LLVM (useful when they are not installed) |
| `-h`, `--help` | help |

Running the result:

```bash
java -cp foo/bar baz     # JVM
lli foo/bar/baz.bc       # LLVM
```

Several files can be given at once; each is compiled independently. The exit code is `0` only if
all of them compiled; errors go to stderr, e.g.:

```text
prog.ins: statement 2: variable 'z' is used before being assigned
prog.ins: parse error: syntax error at line 2, column 4 before `*'
```

Environment variables:

| Variable | Meaning |
|----------|---------|
| `INSTANT_LIB_DIR` | directory containing `jasmin.jar` / `runtime.bc`. By default these are searched in order: `lib/` next to the executable (the layout after `make`), the data directory of `cabal install`, `./lib` |
| `JAVA` | Java command (default `java`) |
| `LLVM_LINK` | llvm-link command (default `llvm-link`) |

The compilers can also be run without `make`, through cabal (from the project root):

```bash
cabal run insc_jvm -- test/programs/basic.ins
```

## Tests

```bash
make test         # everything: unit-test + e2e-test
make unit-test    # cabal test – needs neither Java nor LLVM
make e2e-test     # builds the compilers and runs test/e2e.sh (needs java, llvm-link, lli)
```

- **`test/Spec.hs`** (`cabal test`): unit tests (parser, operator associativity, errors,
  JVM instruction selection, LLVM output) and QuickCheck properties on random programs. The
  generated code is *executed* by a JVM stack simulator and by an interpreter of the emitted
  LLVM IR, and the result is compared with a reference interpreter (32-bit arithmetic). The tests
  also check that `.limit stack` equals exactly the maximum stack depth reached at run time and
  that it is optimal.
- **`test/e2e.sh`**: compiles every `test/programs/*.ins` with both compilers, runs the results
  with `java`/`lli` and compares them with `*.output`; checks that the programs in `test/bad/` are
  rejected; compiles a large generated program (300 variables, an expression nested 1000 deep) and
  checks that JVM and LLVM agree; measures compilation time for a 200,000-statement program
  (complexity).

To add a test, put `name.ins` and its expected output `name.output` in `test/programs/`.

## Running in a container (no GHC needed)

The `Dockerfile` contains the complete toolchain (GHC, cabal, JDK, LLVM). It works with both
Docker and Podman (`make` picks `podman` when available; force Docker with
`make docker CONTAINER=docker`).

```bash
make docker          # builds the instant-compiler image with insc_jvm/insc_llvm compiled
make docker-test     # builds the image and runs make test inside it
```

The same without `make` on the host (only Podman or Docker is needed):

```bash
podman build -t instant-compiler .
```

```bash
podman run --rm instant-compiler make test
```

Compiling your own programs from a `./progs` directory with the image:

```bash
podman run --rm -v "$PWD/progs:/data:Z" instant-compiler sh -c 'insc_jvm /data/prog.ins && java -cp /data prog'
```

```bash
podman run --rm -v "$PWD/progs:/data:Z" instant-compiler sh -c 'insc_llvm /data/prog.ins && lli /data/prog.bc'
```

Developing without a local GHC: use only the `toolchain` stage of the image and mount the project
directory into the container (the `instant-cabal` volume keeps downloaded dependencies between
runs):

```bash
podman build --target toolchain -t instant-toolchain .
```

```bash
podman run --rm -it -v instant-cabal:/root/.local/state/cabal -v "$PWD:/src:Z" -w /src instant-toolchain make test
```

## How it works

```text
             ┌───────────────── Compiler.Frontend ─────────────────┐
 file.ins →  │ lexer/parser (BNFC) → variable and literal checks     │ → Program (AST)
             └───────────────────────────────────────────────────────┘
                     │                                    │
          Compiler.Backend.JVM                  Compiler.Backend.LLVM
     Method {stack, locals, [Instr]}             SSA: %1, %2, ...
                     │                                    │
   file.j → Jasmin → file.class        file.ll → llvm-link (+ lib/runtime.bc) → file.bc
```

**Frontend** (`Compiler.Frontend`): parses the program and rejects anything that cannot be
compiled correctly: a variable used before it is assigned, and literals > 2³¹−1.

**JVM** (`Compiler.Backend.JVM`):
- subexpressions are evaluated in **Sethi–Ullman** order: the subtree that needs the deeper stack
  is computed first, so the declared `.limit stack` is minimal (verified by the tests);
- `swap` is emitted only where the operands of a non-commutative operator (`-`, `/`) were
  reordered; `+` and `*` are treated as commutative, as the task statement allows;
- printing: for an expression of depth 1, `getstatic System.out` comes first (no `swap`); for
  deeper ones the expression comes first, then `getstatic` + `swap` (so the stack does not grow);
- shortest instruction forms: `iconst_m1..5`, `bipush`, `sipush`, `ldc`, `iload_0..3`/`istore_0..3`;
- `.limit locals` = 1 (`args`) + the number of variables.

**LLVM** (`Compiler.Backend.LLVM`): every intermediate value goes into a fresh SSA register and
each variable is bound to the register holding its value, so no `alloca`/`load`/`store` is
needed. Assigning a constant (`x = 5`) emits an explicit `add i32 0, 5`: as the task requires, no
operation is skipped or folded (no constant folding). `printInt` comes from `lib/runtime.bc`.

**Complexity**: all passes are linear (difference lists when concatenating code), with
`Data.Map` for variables, giving O(n log n) overall, which is what the task requires at most.

## Project layout

```text
.
├── Makefile             make / make test / make clean / make grammar / make docker
├── instant.cabal        package definition: library, insc_jvm, insc_llvm, tests
├── Dockerfile           environment with GHC, JDK and LLVM
├── app/
│   ├── insc_jvm.hs      main: frontend → JVM backend → Jasmin
│   └── insc_llvm.hs     main: frontend → LLVM backend → llvm-link
├── src/
│   ├── Instant.cf       language grammar (BNFC)
│   ├── Instant/         generated by BNFC (make grammar): Abs.hs, Lex.x (alex), Par.y (happy)
│   └── Compiler/
│       ├── Syntax.hs    AST view shared by the backends (binary operators, commutativity)
│       ├── Frontend.hs  parsing + variable and literal-range checks
│       ├── Driver.hs    CLI shared by both compilers: files, errors, locating lib/, external tools
│       └── Backend/
│           ├── JVM.hs   Jasmin code generation
│           └── LLVM.hs  LLVM IR generation
├── lib/
│   ├── jasmin.jar       Jasmin assembler
│   └── runtime.bc       LLVM runtime (printInt)
└── test/
    ├── Spec.hs          unit and QuickCheck tests (cabal test)
    ├── e2e.sh           end-to-end tests (java, lli)
    ├── programs/        test programs *.ins + expected output *.output
    └── bad/             programs that must be rejected
```

Changing the grammar: edit `src/Instant.cf` and run `make grammar` (needs `bnfc`, e.g.
`cabal install BNFC`). The `.x`/`.y` files are processed by alex/happy automatically during the
build, so they work with any GHC version (previously the repository contained generated `.hs`
code that only compiled on GHC 8.4).

## Troubleshooting

| Problem | Solution |
|---------|----------|
| `cannot find jasmin.jar; looked in: ...` | you are running an executable outside the project – set `INSTANT_LIB_DIR=/path/to/project/lib` |
| `cannot run llvm-link` / `cannot run java` | install LLVM / Java or point to them with `LLVM_LINK` / `JAVA`; alternatively use `--emit-only` |
| `cabal: unrecognised command: list-bin` | cabal is too old (< 3.4) – upgrade it (`ghcup install cabal`) |
| `java.lang.ClassFormatError: Invalid method Code length` | the program is too large for the JVM (64 KB bytecode limit per method) – a platform limitation; the LLVM version works |
| Error loading `runtime.bc` in a newer LLVM | bitcode is backward compatible (verified with LLVM 14 and 22); if it ever fails, regenerate it from your own `runtime.ll` (`llvm-as runtime.ll -o lib/runtime.bc`) |
| `file name 'my-prog' is not a valid JVM class name` | the class is named after the file, so the file name must be a Java identifier (letters, digits, `_`, `$`) – rename it, e.g. to `my_prog.ins` (only affects `insc_jvm`) |
